# '글 품질 HF API 수치 대조 확정' 보고서(review-content-quality.md) 검토

- 일시: 2026-09-05
- 검토 대상: `docs/verify/review-content-quality.md` (커밋 `f676b9a`, opencode 작성)
- 검토 방법: 대상 글 5개 중 3개(EVIE-Preview-4.5B, granite-4.2-3b, FastVideo…)의 본문과 HF API 응답을 직접 재조회하고, 문단 생성 코드 `build_why_paragraph` 와 `data/stats_history.json` 을 읽어 보고서의 판단 근거를 대조했다.

## 1. 정확한 부분

- 수치 대조(likes·downloads·license·params·createdAt·pipeline_tag)는 재조회 결과와 방향이 맞다. 오늘 시점 downloads 가 더 늘어 있으나(EVIE 2,225→2,255, granite 16,721→17,732) 글이 "수집 시점 2026-09-05" 스냅샷임을 명시하므로 정합성 문제는 아니다.
- 라이선스 상업 이용 문구, 핵심 스펙 표 6행, 관련 모델 링크 200 응답, HF 웹 페이지 200 은 모두 확인된다.

## 2. 누락·과대 평가 (판정에 영향)

Goal 의 글 품질 기준은 "'왜 주목받는가'(선정 이유 + **좋아요/다운로드 추세 수치** + **같은 기관·같은 태스크의 이전 모델 대비 변화**)" 이다. 보고서 3절은 이 두 항목을 충족으로 표시했지만 실제 글은 다음과 같다.

| 기준 | 글의 실제 내용 | 보고서의 표시 | 검토 결론 |
| --- | --- | --- | --- |
| 추세 수치 | "좋아요 95개, 다운로드 2,225회(수집 시점 …)" — 단일 시점 값만 있고 증감·기간이 없다. `stats_history.json` 이력 깊이가 1일(2026-09-05)이라 추세를 낼 수 없는 상태인데, 글에 그 사실도 없다 | "수치 (좋아요/다운로드)" 열로 충족 처리 | **미충족**. 추세 ≠현재값. 산출 불가면 "추세는 이력 1일로 산출 불가" 라고 표기해야 함 |
| 같은 기관·같은 태스크 이전 모델 대비 변화 | "같은 기관(tencent)의 다른 발행 모델 tencent/Hy4-preview 와 함께 살펴보세요" — 링크 안내 문장이며 비교(파라미터·좋아요·다운로드 차이 등)가 없다 | "같은 기관 모델 비교" 열로 충족 처리 | **미충족**. 코드(`build_why_paragraph`)는 org 만 같으면 dict 순서상 첫 모델을 고르고 task 를 보지 않는다. 예: UI-Mate-9B(image-text-to-text)의 비교 대상이 EVIE-Preview-4.5B(visual-document-retrieval), EVIE 의 비교 대상이 Hy4-preview(text-generation) |

보고서는 문단에 "수치가 있고 기관 이름이 언급된다"는 형식 존재만 확인했고, 기준이 요구하는 '추세'와 '대비 변화'의 의미를 검증하지 않았다.

## 3. 사소한 개선점

- 1절에서 FastVideo likes 만 스냅샷 차이를 주석했는데, 다른 4개도 조회 시점에 따라 달라지는 값이므로 "전 항목 스냅샷 기준" 을 절 머리에 한 번 명시하는 편이 일관된다.
- lastModified 를 #1 에만 기록했다. 선정 규칙(60일 신규 / 14일 갱신)과의 정합을 보이려면 5개 모두 createdAt·lastModified 와 어느 게이트로 통과했는지 적어야 한다.
- "무작위 선택" 이라고만 했는데 선택 방법(명령·시드)을 남겨야 재현 가능하다.

## 4. 수정 지시

### 4-a. 글 생성기(구현 담당, 리뷰 대상 아님이지만 재작업 필요)
1. `build_why_paragraph` 에 추세 문장 추가: `stats_history.json` 에서 7일(없으면 가능한 최장 구간) 전 스냅샷과 비교해 "좋아요 +N(기간), 다운로드 +M(기간)" 을 쓰고, 이력이 2일 미만이면 "추세는 수집 이력 부족으로 다음 갱신부터 표기" 라고 명시한다.
2. 비교 대상 선택을 **같은 org 이면서 같은 task** 인 발행 모델로 제한하고, 없으면 같은 task(기관 무관)로, 그것도 없으면 현재의 '비교 제공 불가' 문장을 유지한다. 비교 문장에는 파라미터·좋아요·다운로드 차이를 수치로 쓴다(HF API 값만 사용).
3. 위 두 규칙을 고정하는 단위 테스트(이력 있음/없음, 같은 task 있음/없음) 추가.

### 4-b. 보고서(opencode)
1. 재작업된 글 5개로 3절을 다시 작성하되, '추세 수치' 열에는 증감 수치와 기간을, '비교' 열에는 비교 대상의 task 일치 여부와 차이 수치를 인용한다.
2. 5개 모두 createdAt·lastModified·통과 게이트를 표에 추가한다.
3. 선택 방법과 조회 시각을 기록한다.
